# Решатель задачи планирования информационного взаимодействия

Программа читает описание задачи планирования в XML (формат PDA), решает оптимизационную
задачу и записывает план информационного взаимодействия в формате BPMN.

Задача решается двумя способами: монолитным симплекс-методом и декомпозицией
Данцига-Вульфа. Оба написаны в проекте, внешних библиотек для оптимизации нет.

```sh
sh build.sh
./pda_solver examples/sample_task.xml                 # монолитный симплекс
./pda_solver examples/sample_task.xml --method dw     # декомпозиция
```

---

## 1. Место программы в системе

```
расписание связей (JSON)
        │
        ▼
  DynamicNetwork (Е. А. Кузнецов)   режет время на интервалы постоянства структуры,
        │                           задаёт возможности объектов и связи
        ▼
   задача в XML (формат PDA)
        │
        ▼
  pda_validator.py                  проверяет корректность входного файла
        │
        ▼
  pda_solver (эта программа)        строит задачу ЛП и решает её
        │
        ▼
   план в BPMN
```

Математическая основа — модель планирования информационного взаимодействия кластера
малых КА ДЗЗ (Д. А. Павлов): динамическая потоковая модель интегрируется по интервалам
постоянства структуры и превращается в задачу линейного программирования.

## 2. Сборка

Нужен только компилятор C++17. Библиотека tinyxml2 лежит в `third_party/` двумя файлами,
решатели написаны в проекте. Внешних пакетов ставить не требуется.

```sh
sh build.sh                                  # Linux, macOS
cmake -B build && cmake --build build        # в том числе Windows
```

Для проверки входных файлов нужен Python 3 и `pda_validator.py` рядом с исполняемым
файлом. Проверку можно отключить ключом `--skip-validation`.

Флаг `/utf-8` для MSVC прописан в `CMakeLists.txt`: в исходниках есть строки на русском,
без него Visual Studio выдаёт предупреждения, а в консоли получаются кракозябры.

## 3. Запуск

```
pda_solver <входной.xml> [-o план.bpmn] [--method simplex|dw] [--verbose]
                         [--quiet] [--skip-validation] [--validator путь]
```

| Ключ | Назначение |
|---|---|
| `-o <файл>` | куда записать план, по умолчанию `plan.bpmn` |
| `--method simplex` | монолитный симплекс (по умолчанию) |
| `--method dw` | декомпозиция Данцига-Вульфа |
| `--verbose` | показать ход генерации столбцов |
| `--quiet` | не печатать значения переменных |
| `--skip-validation` | не запускать валидатор |
| `--validator <путь>` | путь к `pda_validator.py`, если он лежит не рядом |

Переменные окружения: `PDA_SIZES=1` печатает размеры матриц, `PDA_DEBUG=1` — диагностику
решателя.

Пример вывода:

```
Валидация: ошибок нет.
Интервалов: 4, потоков: 2, технологий обработки: 1, передачи: 1
Метод: декомпозиция Данцига-Вульфа
Блоков: 5, связующих ограничений: 4, итераций: 5, сгенерировано столбцов: 20
Статус решателя: Оптимум найден (Данциг-Вульф)
Значение критерия: 54700.0000

Баланс данных:
  поступило извне          87640.0000
  доставлено потребителю   54700.0000  (62.4 %)
  осталось в ЗУ            32940.0000  (37.6 %)
  потеряно                     0.0000  (0.0 %)
Проверка плана: баланс потоков и ограничения по времени выполнены.

План записан в plan.bpmn: цепочек 4, задач 37
```

Коды возврата: `0` — успех, `1` — ошибки валидации или аргументов, `2` — оптимальное
решение не получено, `3` — исключение при разборе или записи.

```
│   ├── simplex.*        двухфазный симплекс-метод, двойственные оценки
│   ├── dw.*             декомпозиция Данцига-Вульфа
│   ├── check.*          независимая проверка плана и сводка по балансу
│   ├── bpmn.*           запись плана в BPMN
│   └── main.cpp         разбор аргументов и конвейер
│
├── tests/
│   ├── test_main.cpp    тесты всех уровней
│   └── run_tests.sh     сборка и запуск тестов
│
├── tools/
│   ├── gen_task.py      генератор задач для экспериментов
│   └── bench.sh         замеры двух методов
│
├── third_party/         tinyxml2
└── examples/
    ├── sample_task.xml  4 объекта сбрасывают данные на центр за 4 интервала
    └── tight_task.xml   то же с малым ЗУ — появляются потери
```

Зависимости между модулями линейные, без циклов:

```
main.cpp → parser → model
         → lp → simplex, model
         → dw → simplex, lp, model
         → check → lp, model
         → bpmn → lp, model
```

`model.h` не зависит ни от чего. tinyxml2 попадает в код только в `parser.cpp` и
`bpmn.cpp` — на границах ввода и вывода. Решатели не знают ни про XML, ни про BPMN.

## 5. Модель

Переменные (все неотрицательны, в единицах объёма):

| Переменная | Смысл | В постановке |
|---|---|---|
| `transport[k,i,j,t]` | передано из i в j технологией t на интервале k | x_ijρk |
| `process[k,i,d]` | переработано технологией d (объём входа) | g_iρdk |
| `storage[k,i,ρ,s]` | осталось в ЗУ на конец интервала | y_iρk |
| `lost[k,i,ρ]` | потеряно | z_iρk |
| `resultflow[k,i,ρ]` | выдано потребителю | — |

Ограничения:

1. **Баланс потоков** по каждой тройке (интервал, объект, тип потока): поступление извне,
   принятое по каналам, выход процессов и остаток с прошлого интервала равны отправленному,
   потреблённому процессами, сохранённому, потерянному и выданному — формула (4).
2. **Ёмкость ЗУ**: сумма хранимых потоков не больше значения `storage_*` — формула (6).
3. **Время**: обработка, отправка и приём не превышают длительности интервала либо
   значений `total_capacity`, `send_capacity`, `receive_capacity` — формулы (7)–(8).
4. **Взаимное исключение направлений канала**: по двустороннему каналу суммарная
   длительность передачи в обе стороны не больше длительности интервала.
5. **Пользовательские ограничения** из раздела `constraints` входного файла.

Критерий берётся из `selectors` и `criterion`: взвешенная сумма раскрытых по `*`
переменных — свёртка (10). Переменные `process` и `transport` в селекторах означают
длительности операций, а не объёмы, поэтому их коэффициенты домножаются на `time / size`.

## 6. Два решателя

### Монолитный симплекс

Вся задача собирается в одну систему и решается двухфазным симплекс-методом с плотной
таблицей. Таблица обновляется на каждом шаге; каждые 200 шагов пересчитывается из
исходной матрицы, чтобы не накапливалась ошибка округления. При серии вырожденных шагов
включается правило Блэнда.

### Декомпозиция Данцига-Вульфа

Блок — один объект со всеми его интервалами: его балансы, ёмкость памяти, лимиты времени.
Связывают блоки только передачи. Главная задача выбирает веса планов блоков и возвращает
цены на приём (двойственные оценки связующих ограничений); блок по этим ценам ищет свой
лучший план. Когда ни один блок не предлагает плана выгоднее имеющихся, решение оптимально.

Начальное решение строится явно: каждому блоку даётся тривиальный план — ничего не
передавать, всё поступившее списать в потери. Он допустим при любых данных и не даёт
вклада в связующие ограничения, поэтому главная задача допустима с первой итерации.

Четыре особенности реализации, без которых метод не работает устойчиво:

- **Тривиальный стартовый план** вместо искусственных переменных со штрафом. При объёмах
  порядка 10⁵ штраф выходит порядка 10⁸, и симплекс зацикливается на вырожденных шагах.
- **Агрегирование связующих ограничений по получателю**: одна строка на тройку
  (интервал, получатель, технология) вместо строки на каждый канал. Получателю достаточно
  суммарного принятого объёма по технологии. Это дало основной выигрыш.
- **Относительные допуски**: при коэффициентах порядка 10⁵ абсолютный допуск 10⁻⁹ тонет
  в шуме округления, и симплекс бесконечно пивотирует на мнимых улучшениях.
- **Рефакторизация базиса**, см. выше.

### Размеры матриц

Задача из 16 объектов и 40 интервалов:

| | Монолит | Декомпозиция |
|---|---|---|
| Переменных | 2932 | 172–280 в подзадаче |
| Ограничений | 2292 | до 200 в подзадаче |
| Рабочая таблица | ≈ 2292 × 5200 (12 млн ячеек) | 16 штук по ≈ 200 × 500 |
| Главная задача | — | 56 строк |

Подзадача растёт как O(|K|) и не зависит от числа объектов, монолитная таблица — как
O(|N|²·|K|²). Посмотреть размеры: `PDA_SIZES=1 ./pda_solver задача.xml`.

### Замеры

| Задача (объекты × интервалы) | Монолит | Декомпозиция | Критерий |
|---|---|---|---|
| 5 × 8 | 0,02 с | 0,01 с | 88 000, совпадает |
| 8 × 15 | 0,21 с | 0,05 с | 222 000, совпадает |
| 12 × 25 | 3,04 с | 0,44 с | 492 000, совпадает |
| 16 × 40 | 84,7 с | 2,12 с | 168 000, совпадает |
| 20 × 60 | не считается | 12 с | — |
| 30 × 90 | не считается | 127 с | — |

Воспроизвести: `bash tools/bench.sh 3`. Скрипт генерирует задачи (генератор детерминирован
по зерну), прогоняет оба метода, повторяет замеры и печатает медиану.

Базой сравнения служит монолитная реализация с плотной таблицей. Тестовые задачи имеют
топологию звезды: периферийные объекты передают в единственный центр.

## 7. Проверка результата

**Независимая проверка плана** (`check.cpp`) пересчитывает балансы, занятость ЗУ и затраты
времени заново, не заглядывая в матрицы решателя. Поэтому ловит ошибки не только в
решении, но и в самой сборке модели.

**Сводка по балансу** показывает, куда делись все поступившие данные: доставлено,
осталось в ЗУ, потеряно. Если технология обработки меняет объём (сжимает или наращивает
поток), разница выводится отдельной строкой «изменение при обработке».

**Согласие двух методов**: монолит и декомпозиция решают одну и ту же задачу, поэтому
значения критерия обязаны совпадать. Это основная проверка правильности декомпозиции.

**Тесты**:

```sh
sh tests/run_tests.sh
```

68 проверок на четырёх уровнях: симплекс на задачах с известным ответом (включая
несовместность, неограниченность и двойственные оценки); разбор XML и направления связей;
модель на задачах, решаемых вручную — лимит времени и нехватка ЗУ срабатывают
предсказуемо; согласие двух методов и корректность плана на обоих примерах; выгрузка BPMN.

## 8. Формат входного XML

```xml
<XMLDocument version="1.0">
  <task>
    <flows>                                   <!-- типы информационных потоков -->
      <type id="1" price="1" loss="1"/>
    </flows>

    <process>                                 <!-- технологии обработки -->
      <type id="1" time="0.004">
        <input><type id="1" size="1"/></input>
        <output><type id="2" size="1"/></output>
      </type>
    </process>

    <transport>                               <!-- технологии передачи -->
      <type id="1" time="0.05">
        <input><type id="1" size="1"/></input>
        <output><type id="1" size="1"/></output>
      </type>
    </transport>

    <storage>                                 <!-- типы запоминающих устройств -->
      <type id="1"><input><type id="1"/><type id="2"/></input></type>
    </storage>

    <struct id="1" time="1431" start_time="0" end_time="1431">
      <elem id="1" output_2="" process_1="" storage_1="50000"/>
      <elem id="3" input_1="14310" storage_1="20000"/>
      <link id1="3" id2="1" direction="forward" transport_1=""/>
    </struct>

    <selectors>
      <selector id="1" sign="1"><resultflow object="*" flow="2" interval="*"/></selector>
      <selector id="2" sign="-1"><lost object="*" flow="*" interval="*"/></selector>
    </selectors>

    <criterion sign="MAX"><selector id="1"/><selector id="2"/></criterion>
  </task>
</XMLDocument>
```

Атрибуты объекта (`elem`):

| Атрибут | Смысл |
|---|---|
| `input_<поток>` | объём поступления потока извне на этом интервале |
| `output_<поток>` | объект является потребителем этого потока |
| `process_<технология>` | технология обработки доступна на объекте |
| `storage_<технология>` | ёмкость ЗУ; `*` означает число длины интервала |
| `send_capacity`, `receive_capacity`, `total_capacity` | лимиты времени; `*` означает длительность интервала |

Атрибуты связи (`link`): `id1`, `id2`, `direction` (`forward`, `backward`, `both`, `none`),
`transport_<технология>`.

Типы переменных в селекторах: `inputflow`, `resultflow`, `process`, `process_all`,
`to_process`, `from_process`, `transport`, `transport_all`, `to_transport`,
`from_transport`, `storage`, `lost`, `time`. Индексы — целые числа или `*`.

Скорости из выгрузки DynamicNetwork попадают в файл так: `proc_speed` становится тактом
технологии обработки, `net_speed` — тактовым объёмом передачи (`size`), `storage_size` —
объёмом `storage_1`.

Семантика формата: длительность операции равна объём × `time` / `size`; переменные
`process` и `transport` в селекторах означают длительности, а не объёмы; `capacity`
ограничивают время, `storage_` — объём; значение `*` означает «правая часть равна длине
интервала»; числа в `process_` и `transport_` ограничений не задают, учитывается только
наличие атрибута.

## 9. Формат выходного BPMN

План оформляется как схема бизнес-процесса в пространстве имён `https://litsam.ru` и
открывается в любом BPMN-редакторе.

- `<resource>` — объект-исполнитель с параметрами `name`, `threads`, `productivity` и по
  одному параметру `performance` на каждую задачу.
- `<task>` — действие плана, например «Передача потока исполнителем 3 исполнителю 1
  способом 1 на интервале 1».
- `<ltsm:props stream="..." volume="...">` — объём потока и время выполнения в секундах.
- `<ltsm:availability>` — границы интервала в абсолютном времени.
- `<sequenceFlow>` и два `<parallelGateway>` — цепочки действий.
- `<bpmndi:BPMNDiagram>` — координаты фигур и линий.

Соотношение: `volume = stream / performance`. Передача 14310 единиц при производительности
20 ед/с занимает 715,5 с.
